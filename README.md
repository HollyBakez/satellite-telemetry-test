# Satellite Telemetry Dashboard

## My approach:

The take home test asked build a full-stack application for a satellite telemetry dashboard.

To keep things simple, I built the backend server using Python + FastAPI, and for the frontend used React, Typescript, and Material UI.

The backend exposes the required REST API endpoints - GET /telemetry - POST /telemetry - GET /telemetry/:id - DELETE /telemetry/:id

I went with a simple array as my in-memory database to ensuure data persistence during runtime. I did seperate it into its own db layer and a repository layer so that if I were to use a DB or cloud provider such as AWS, we could simply modify those files instead of needing to rearchitect many areas. Even though it is in-memory, the functions do take into account is async calls or transactions such that if it was done with a real database then it would be compatible.

For the frontend I kept the components and the api services separate and utilized both Typescript typing and Pydantic schemas to validate incoming API requests.
For the frontend I also went with the backend integration route for making calls to the endpoints, so both backend and frontend will need to run to test the frontend.

I also implemented all the bonus features for both frontend and backend tasks.

### Bonus features (backend):

- The pagination support is available when making API calls, however for simplicity on the frontend side I kept it to a default to request for all data from the database.
- Unit tests for the API endpoints are implemented
- Dockerfile is included for docker support and easy deployment

### Bonus features (frontend):

- Table has sorting functionality for each column
- Error handling is implemented and appropriate error messages are displayed
- Unit tests are included for the key components and for the api services
- Loading spinner and indicators while fetching data from the backend is also implemented.

## Assumptions Made:

- For pagination behavior, there wasn't any explicit limits mentioned so I gave the option to retrieve 'all' telemetry database entries, however in a real-world scenario we may not want this since there could be many entries. But in this test I'm assuming database size would be reasonable.
- For altitude and velocity I went with the assumption that the business logic would require floats over using just ints. Since the prompt doesn't specify beyond number, to make sure the API is flexible for different use cases I decided to go with float for my schema.
- timestamps are provided by the client and are not generated by the backend
- Even though I'm using a in-memory database array solution, I assume to keep things flexible and migratable, I included an additional id field to account for row ids that would be in a real DB, and used uuid to autogenerated an id for telemetry entries.
- Status in the request body was listed to be a string, and I'm going with the assumption that the API could be used by different users who may have different status values. So instead of using enum strings with predefined values, I went with just string and letting users input any status values. However in a real-world scenario there could be requirements or predefined status enums I'd use instead.
- Requirements didn't state needing to indicate when the last refresh/fetch to the telemetry database was done, however I assumed that there could be cases where the backend server is down or the frontend could lose connection to the backend and data could be stale. So I implemented a last fresh timestamp and a backend health check indicator for user convenience.

## Project Structure

- `backend/` — FastAPI for backend task

## Prerequisites

- Python 3.15
- Node.js and npm

## How to run Backend

You can run the backend locally or via Docker, I recommend using the docker method.

### How to run locally (no docker)

```bash
cd backend
python -m venv .venv
```

Activate the virtual environment, then run:

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

The backend API will be available at http://localhost:8000, with interactive API documentation at http://localhost:8000/docs.


### How to run using Docker
```bash
# Build the backend image
cd backend 
docker build -t telemetry-backend .
```

```bash
# Start backend container
docker run --rm -d --name telemetry-backend -p 8000:8000 telemetry-backend
```
The backend API will be available at http://localhost:8000, with interactive API documentation at http://localhost:8000/docs.

### How to run backend tests

From the `backend/` directory:

```bash
python -m pytest -v
```

## How to run Frontend

Open a separate terminal:

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173/ in your browser.


## How to test the application
#### Start up the backend either using local or docker method. I will show the docker method.
```bash
# Build the backend image
cd backend 
docker build -t telemetry-backend .
```

```bash
# Start backend container
docker run --rm -d --name telemetry-backend -p 8000:8000 telemetry-backend
```
#### Start up the frontend.

```bash
cd frontend
npm install
npm run dev
```
Open http://localhost:5173/ in your browser.

Verify that Health Status: Online, it could take 30 secs - 1 min, frontend will check server health on start-up.

1. Start by adding some telemetry entries.
2. Test out the filters.
3. Test out sorting each column.
4. Delete some entries.
5. Stop the backend server.
6. The frontend will show backend api health status offline.
7. Click refresh, try add telemetry, or delete telemetry and a error message will show.
8. Start up backend server again.
9. Once backend api health status is online again, click refresh and the table will clear since the backend server was restarted and the database is cleared.
